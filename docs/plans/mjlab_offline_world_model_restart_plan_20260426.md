## How To Use This Document

This document has two layers:

1. **Master protocol**: the full paper-grade protocol we eventually want for a top-tier AI conference submission.
2. **Phase-A execution sheet**: the smaller first execution path that should be run now to avoid spending weeks on infrastructure before answering the feasibility question.

The first execution should not run every dataset variant, every model variant, policy extraction, and online fine-tuning at once. The first execution should answer:

```text
Under a fixed, correctly collected MJLab offline dataset, can Flow-based world models fit the data at all?
```

We do not require compute parity in the first feasibility pass. If Flow needs longer training or more ODE substeps to win, we allow that, because the immediate scientific question is whether Flow can win at all. However, all compute differences must be logged:

```text

number of model evaluations / ODE substeps
peak GPU memory
```

Compute-matched reporting is a later analysis axis, not the first go/no-go criterion.

## 0. Why We Are Restarting

The previous experiments produced useful negative evidence, but they are not sufficient as a paper-grade experimental foundation because the pipeline had too many possible confounders:

1. The model-based RL pipeline was not fully separated into data collection, world-model supervised learning, imagined policy optimization, and real-environment evaluation.
2. The MJLab data collection protocol was too small and too informal. It produced fixed windows directly, but did not persist raw episodes, command metadata, collector quality, resolved task IDs, or held-out split definitions at a publishable standard.
3. The previous comparison mixed architecture, dataset distribution, training objective, and sometimes environment fallback assumptions.
4. The current pure Flow world model did not fit the training dynamics under the shared rollout metric, but we need to verify this under a cleaner, reviewer-defensible dataset and pipeline.

The restart goal is therefore not immediately:

```text
Show Flow WM beats MLP WM.
```

The first goal is:

```text
Build a correct MJLab offline data and model-based RL pipeline, then prove that world-model pretraining is feasible and measurable under fixed data.
```

Only after that should we run the full Flow-vs-MLP and WM-vs-policy-side comparisons.

## 1. Core Research Question

We want to test whether Flow-based components improve policy learning in PWM-style model-based RL on MJLab.

The controlled 2x2 question is:

| World model | Policy | Meaning |
|---|---|---|
| MLP WM | MLP/Gaussian policy | PWM-style baseline |
| Flow WM | MLP/Gaussian policy | Flow as learned surrogate dynamics |
| MLP WM | Flow policy | Flow as action distribution / policy class |
| Flow WM | Flow policy | Full Flow variant |

However, this 2x2 should not be run as the first experiment. A Flow WM that cannot fit a fixed offline dataset should not be used as the main dynamics model in downstream policy learning.

The first gate is:

```text
Can each candidate world model learn a fixed MJLab offline dataset well enough to support stable imagined rollouts?
```

## 2. Literature Anchors and What We Use From Each

### 2.1 PWM

PWM uses a fixed offline dataset to train a world model, then trains the policy through differentiable imagined rollouts inside that world model. In the multi-task experiments, the paper reports using the same data and world-model setup as TD-MPC2: 120k trajectories per dm_control task and 40k trajectories per MetaWorld task, generated by 3 TD-MPC2 seeds. It pretrains the world model with horizon `H = 16` and discount `gamma = 0.99` for better first-order gradients.

Source: https://policy-world-model.github.io/media/pwm.pdf

What we adopt:

```text
1. Use one shared offline dataset before policy extraction.
2. Train the world model as supervised latent dynamics and reward prediction.
3. Train policy inside the learned world model using first-order gradients.
4. Report not only model loss, but also whether the model produces useful policy gradients.
```

Critical interpretation:

PWM does not imply that the most accurate dynamics model is always best. PWM's central point is that the learned world model should be a useful differentiable surrogate for first-order gradient policy learning. Therefore, our evaluation must include rollout stability, gradient quality, and downstream policy reward, not just one-step prediction error.

### 2.2 Newt

Newt first pretrains on demonstrations and then improves through online interaction across tasks. Its demonstration dataset contains 10-40 demonstrations per task, 4020 total demonstrations, collected by single-task TD-MPC2 agents trained from low-dimensional observations. It rejects failed or substantially low-return episodes when building expert demonstrations.

Source: https://www.nicklashansen.com/NewtWM/newt.pdf

What we adopt:

```text
1. Expert or teacher data is useful as an anchor.
2. Demonstrations should be metadata-rich and generated by reproducible collector policies.
3. Online replay should not erase demonstration data too quickly.
```

Critical interpretation:

Newt's pretraining data is not primarily "bad-to-good policy replay." It is expert demonstrations. The weak-to-good distribution appears naturally in online replay after pretraining. Therefore, for MJLab we should not claim Newt directly motivates a weak-to-good offline pretrain dataset. It motivates teacher anchors and careful demo/replay mixing.

### 2.3 RWM / RWM-U / Offline RWM

RWM-style methods emphasize training policies from learned robotic world models. The offline RWM-U paper explicitly targets offline model-based RL from existing datasets and highlights compounding error and distribution shift in long-horizon rollouts.

Source: https://arxiv.org/abs/2504.16680

Related RWM-style offline evaluations compare dataset quality categories such as random, medium, expert, and mixed replay collected from PPO training stages.

What we adopt:

```text
1. Offline robotic data should be stratified by collector quality.
2. Mixed replay is valuable because it includes failures, recovery, partial skill, and expert behavior.
3. Long-horizon rollout stability must be evaluated directly.
```

Critical interpretation:

The useful idea is not "collect any mixed data." The useful idea is to define collector quality bins before training the world models, keep the dataset fixed, and let all world-model variants train on the same data.

## 3. Correct Model-Based RL Pipeline

The pipeline must separate data flow from gradient flow.

### 3.1 Objects and Notation

Let the real MJLab environment define:

```math
s_{t+1} \sim p_{\mathrm{env}}(\cdot \mid s_t, a_t),
\qquad
r_t = r_{\mathrm{env}}(s_t, a_t),
\qquad
d_t \in \{0,1\}.
```

Here:

```text
s_t: raw state / observation from MJLab
o_t^{phys}: physical model observation after preprocessing, excluding exogenous command scheduler state
o_t^{model}: full model-side observation if implementation concatenates physical observation and command
a_t: continuous action
r_t: true environment reward
d_t: termination or truncation flag
c_t: task command, for example target velocity command
e: task ID / embodiment ID
```

For velocity-conditioned MJLab tasks, command handling is not optional, but command must be separated by role:

```text
dynamics target:
  physical state only

reward / policy / value:
  physical latent plus command
```

Canonical Phase-A protocol:

```math
z_t = E_\phi(o^{phys}_t, e),
```

```math
\hat z_{t+1} = F_\phi(z_t, a_t, e),
```

```math
\hat r_t = R_\phi(z_t, a_t, c_t, e).
```

The policy and value function are command-conditioned:

```math
a_t \sim \pi_\theta(\cdot \mid z_t,c_t,e),
\qquad
V_\psi(z_t,c_t,e).
```

Rationale:

```text
Velocity command is an exogenous scheduler variable. The physical transition should not be forced to predict command changes. Reward, policy, and value depend on command, so command cannot be metadata only.
```

If an implementation receives MJLab observations with command already concatenated, the collector must split it into `phys_obs` and `commands` before building WM dynamics targets. The dataset report must list observation fields, command dimensions, and the exact split rule.

The offline dataset is:

```math
\mathcal{D}_{\mathrm{off}}
=
\{
\tau_i
\}_{i=1}^N,
\qquad
\tau_i =
(s_0, a_0, r_0, d_0, c_0, \ldots, s_T).
```

The world model is:

```math
M_\phi = (E_\phi, F_\phi, R_\phi, T_\phi),
```

where:

```math
z_t = E_\phi(o^{phys}_t, e),
\qquad
\hat z_{t+1} = F_\phi(z_t, a_t, e),
\qquad
\hat r_t = R_\phi(z_t, a_t, c_t, e).
```

`T_phi` is optional termination prediction. For the first restart stage, termination prediction is logged but not required unless the downstream task uses terminations heavily.

The policy and critic are:

```math
a_t \sim \pi_\theta(\cdot \mid z_t, c_t, e),
\qquad
V_\psi(z_t, c_t, e) \approx
\mathbb{E}_{\pi_\theta}
\left[
\sum_{k=0}^{\infty}\gamma^k r_{t+k}
\mid z_t,c_t
\right].
```

### 3.2 Real Environment Rollout

Real rollout is non-differentiable environment interaction:

```math
a_t \sim \pi_\beta(\cdot \mid s_t, c_t, e),
\qquad
s_{t+1}, r_t, d_t \leftarrow \mathrm{MJLab.step}(a_t).
```

Here `pi_beta` is the data collector policy, not necessarily the final policy.

The result is appended to the real dataset:

```math
(s_t, a_t, r_t, s_{t+1}, d_t, c_t, e, \mathrm{metadata})
\in
\mathcal{D}_{\mathrm{off}}.
```

No policy gradient passes through MJLab.

### 3.3 World-Model Supervised Pretraining

Given a window:

```math
w_t =
(s_t, a_t, r_t, d_t, \ldots, s_{t+H}),
```

the world model is trained by supervised prediction in latent space.

For an MLP world model:

```math
\hat z_t = E_\phi(o^{phys}_t, e),
```

and autoregressive rollout is:

```math
\hat z_{t+h+1}
=
F_\phi(\hat z_{t+h}, a_{t+h}, e),
\qquad
h = 0,\ldots,H-1.
```

Targets are encoded observations:

```math
z^*_{t+h}
=
\mathrm{sg}(E_\phi(o^{phys}_{t+h}, e)),
```

where `sg` means stop-gradient.

For windows that contain a true terminal transition, include the final valid transition into the terminal state, but mask losses after `done=True`.

Convention:

```text
d_t = 1 means action a_t produced terminal next state s_{t+1}.
```

Therefore the first transition into the terminal state must still contribute to the dynamics loss. Define the dynamics rollout mask:

```math
m^{dyn}_{t,h}
=
\prod_{j=0}^{h-2}(1-d_{t+j}),
\qquad
h \ge 1.
```

The empty product at `h=1` is defined as 1. This keeps the valid transition `(s_t, a_t) -> s_{t+1}` even when `d_t=True`, and masks only predictions after the terminal state.

The masked H-step rollout dynamics loss is:

```math
\mathcal{L}^{H}_{\mathrm{dyn}}
=
\frac{
\sum_{h=1}^{H}
m^{dyn}_{t,h}\gamma^{h-1}
\left\|
\hat z_{t+h} - z^*_{t+h}
\right\|_2^2
}{
\sum_{h=1}^{H}m^{dyn}_{t,h}\gamma^{h-1}+\epsilon
}.
```

This means:

```text
include: s_t, a_t -> s_{t+1}, done=True
exclude: terminal/reset boundary transition
mask: all rollout losses after done=True
```

The H-step rollout dynamics loss is:

```math
\mathcal{L}^{H}_{\mathrm{dyn}}
=
\frac{1}{H}
\sum_{h=1}^{H}
\gamma^{h-1}
\left\|
\hat z_{t+h} - z^*_{t+h}
\right\|_2^2.
```

The unmasked expression above is valid only for windows with no true termination inside the horizon. The implementation must use the masked version whenever a done flag appears inside the window.

The reward loss must use the same terminal-boundary convention. The reward `r_{t+h}` belongs to transition `(s_{t+h}, a_{t+h}) -> s_{t+h+1}` and is valid even if that transition terminates the episode. Define:

```math
m^{rew}_{t,h}
=
\prod_{j=0}^{h-1}(1-d_{t+j}),
\qquad
h \ge 0,
```

with the empty product at `h=0` equal to 1. The masked reward loss is:

```math
\mathcal{L}^{H}_{\mathrm{rew}}
=
\frac{
\sum_{h=0}^{H-1}
m^{rew}_{t,h}\gamma^h
\ell_{\mathrm{rew}}
\left(
R_\phi(\hat z_{t+h}, a_{t+h}, c_{t+h}, e),
r_{t+h}
\right)
}{
\sum_{h=0}^{H-1}m^{rew}_{t,h}\gamma^h+\epsilon
}.
```

The world-model loss is:

```math
\mathcal{L}_{\mathrm{WM}}
=
\lambda_{\mathrm{dyn}}\mathcal{L}^{H}_{\mathrm{dyn}}
+
\lambda_{\mathrm{rew}}\mathcal{L}^{H}_{\mathrm{rew}}
+
\lambda_{\mathrm{term}}\mathcal{L}^{H}_{\mathrm{term}}.
```

For the first feasibility stage:

```text
lambda_dyn = 1.0
lambda_rew = 1.0
lambda_term = 0.0 unless termination prediction is enabled.
```

### 3.3.1 Cross-Model Latent Comparability

The primary feasibility question compares MLP WM and Flow WM. A naive latent MSE is not automatically comparable across models if each model trains its own encoder:

```math
\left\|
\hat z_{t+h}
-
\mathrm{sg}(E_\phi(o^{phys}_{t+h},e))
\right\|_2^2
```

is measured inside that model's own latent space. Therefore, every feasibility run must report normalized latent metrics and scale diagnostics.

Normalized rollout dynamics MSE:

```math
\widetilde{\mathcal{L}}^{H}_{\mathrm{dyn}}
=
\frac{
\mathcal{L}^{H}_{\mathrm{dyn}}
}{
\mathrm{Var}(z^*_{t:t+H})+\epsilon
}.
```

Required latent diagnostics:

```text
target_latent_mean
target_latent_std
pred_latent_mean
pred_latent_std
target_latent_norm
pred_latent_norm
latent_norm_ratio = median(||z_pred||) / median(||z_target||)
normalized_one_step_dyn_mse
normalized_rollout_dyn_mse_H8
normalized_rollout_dyn_mse_H16
```

Shared/frozen encoder evaluator:

```text
1. Train one reference MLP encoder E_ref on D_QS_core.
2. Freeze E_ref.
3. Evaluate all model predictions after mapping observations/targets into the same reference latent space when possible.
```

For A3 Medium Feasibility, use two metric lanes:

```text
Primary diagnostic metric:
  own-latent normalized rollout MSE

Primary claim metric:
  shared-latent rollout MSE or frozen-encoder rollout MSE
```

The shared/frozen encoder metric is not required for A0/A1/A2 smoke. It is required before A3 can be called a formal Medium Feasibility result. Without it, A3 may only be reported as an internal diagnostic showing that a model matches under its own normalized latent rollout metric.

A3 must freeze the evaluator choice before any A3 training result is inspected. The default A3 claim lane is:

```text
Primary A3 claim lane:
  frozen shared encoder E_ref

Secondary A3 diagnostic lane:
  each model's own latent space
```

Allowed A3 comparability options:

```text
Option 1:
  Train one reference encoder E_ref with mlp_ref or a self-supervised objective.
  Freeze E_ref.
  Train/evaluate all candidate dynamics in z_ref.

Option 2:
  Use identical encoder architecture and initialization for all WMs.
  Freeze the encoder for all main WM comparisons.

Option 3:
  Allow separate encoders only for exploratory diagnostics.
  Do not use separate-encoder metrics for the main Flow-vs-MLP feasibility claim.
```

### 3.4 Flow World Model Transition

For a Flow WM, the transition is parameterized by a velocity field:

```math
v_\phi(z_\tau, a_t, \tau, e),
\qquad
\tau \in [0,1].
```

Given current latent:

```math
z_s = \hat z_t,
```

and target latent:

```math
z_* = \mathrm{sg}(E_\phi(o^{phys}_{t+1}, e)),
```

the default linear path is:

```math
z_\tau = (1-\tau)z_s + \tau z_*,
\qquad
\tau \sim U[0,1].
```

The default target velocity is:

```math
u^* = z_* - z_s.
```

The flow matching loss is:

```math
\mathcal{L}_{\mathrm{FM}}
=
\mathbb{E}_{\tau}
\left[
\left\|
v_\phi(z_\tau, a_t, \tau, e)
-
u^*
\right\|_2^2
\right].
```

At rollout time, the next latent is obtained by ODE integration:

```math
\hat z_{t+1}
=
z_s + \int_0^1 v_\phi(z(\tau), a_t, \tau, e)\,d\tau.
```

In implementation this is approximated by Euler or Heun with `K` substeps.

Important: the Flow loss value is not directly comparable to the MLP dynamics MSE because the objectives differ. Fair comparison must use shared evaluation metrics:

```text
one-step latent endpoint MSE
H-step autoregressive rollout latent MSE
reward prediction error
downstream policy reward
compute-normalized reward
gradient quality metrics
```

### 3.5 Imagined Rollout and Policy Optimization

Policy optimization happens inside the learned world model.

Sample a real start state:

```math
s_0 \sim \mathcal{D}_{\mathrm{off}},
\qquad
z_0 = E_\phi(o^{phys}_0, e).
```

Then imagine:

```math
a_h \sim \pi_\theta(\cdot \mid z_h, c_h, e),
```

```math
\hat r_h = R_\phi(z_h, a_h, c_h, e),
```

```math
z_{h+1}=F_\phi(z_h,a_h,e),
\qquad
h=0,\ldots,H_{\pi}-1.
```

The actor objective is:

```math
J_{\mathrm{model}}(\theta)
=
\mathbb{E}
\left[
\sum_{h=0}^{H_{\pi}-1}
\gamma^h \hat r_h
+
\gamma^{H_{\pi}} V_\psi(z_{H_{\pi}},c_{H_{\pi}},e)
\right].
```

Actor update:

```math
\theta \leftarrow
\theta
+
\eta_\theta
\nabla_\theta J_{\mathrm{model}}(\theta).
```

The gradient path is:

```text
policy -> action -> learned WM transition/reward -> model return
```

not:

```text
policy -> MuJoCo -> true return
```

The critic target may use lambda returns:

```math
G_h^{(n)}
=
\sum_{i=h}^{h+n-1}
\gamma^{i-h}\hat r_i
+
\gamma^n V_\psi(z_{h+n},c_{h+n},e),
```

```math
\hat V^\lambda(z_h,c_h)
=
(1-\lambda)
\sum_{n=1}^{H_\pi-h-1}
\lambda^{n-1}G_h^{(n)}
+
\lambda^{H_\pi-h-1}G_h^{(H_\pi-h)}.
```

Critic loss:

```math
\mathcal{L}_V(\psi)
=
\sum_h
\left\|
V_\psi(z_h,c_h,e)
-
\mathrm{sg}(\hat V^\lambda(z_h,c_h))
\right\|_2^2.
```

### 3.6 Online Fine-Tuning Loop

After offline pretraining and policy extraction, the online version is:

```text
1. Current policy acts in MJLab.
2. Real transitions are appended to replay.
3. WM is updated on a mixture of offline and online replay.
4. Actor/critic are updated inside the WM by imagined rollouts.
5. Repeat.
```

For the first online stage, use a conservative replay mix:

```text
first 100k online environment steps:
  50% offline pretrain replay
  50% online replay

after 100k online environment steps:
  25% offline pretrain replay
  75% online replay
```

This is a practical compromise inspired by Newt-style retention of demonstration data while still letting online replay adapt.

### 6.2 Collector Policy Strategy

Primary collector:

```text
neutral MLP/Gaussian baseline collector
```

Default implementation decision:

```text
Train the collector ourselves using the existing repo's MJLab-compatible online training path.
```

Reason:

```text
This is more reproducible and less confounded than using unknown open-source checkpoints.
```

Open-source or previously trained checkpoints may be used only if all of the following are true:

```text
1. Exact task ID matches.
2. Observation space matches.
3. Action space and action scaling match.
4. Reward definition matches.
5. Command distribution matches.
6. Termination/truncation semantics match.
7. License permits use.
8. Checkpoint provenance is stored in the dataset manifest.
```

If any condition fails, the checkpoint can be used for a sidecar dataset but not for the main fair dataset.

### 6.3 Collector Seeds and Checkpoint Selection

Train collector seeds:

```text
collector_seed in {0, 1, 2}
```

Evaluate every saved checkpoint on:

```text
100 episodes per task and collector seed
```

Define normalized collector quality:

```math
q(\pi)
=
\frac{
J(\pi)-J_{\mathrm{random}}
}{
J_{\mathrm{best}}-J_{\mathrm{random}}+\epsilon
}.
```

Here:

```text
J(pi): mean evaluation return of checkpoint pi
J_random: mean return of random-smooth collector
J_best: best mean return among all neutral collector checkpoints for that task
epsilon = 1e-8
```

Quality bins:

```text
random-smooth: hand-coded smooth random controller
weak:          q(pi) in [0.10, 0.30)
medium:        q(pi) in [0.30, 0.70)
expert:        q(pi) in [0.80, 1.00]
expert-noisy:  expert policy plus action noise
```

The expert bin also requires absolute task-quality checks:

```text
expert:
  normalized_quality >= 0.8
  fall_rate <= 10%
  episode_length_mean >= 0.9 * max_episode_length
```

If a task-specific reward or success threshold is available, add it to the expert criterion:

```text
expert_return_mean >= task_specific_expert_threshold
```

This prevents a weak collector from producing a fake "expert" bin merely because it is the best among bad checkpoints.

Normalized quality is only used within a task. Do not compare `q=0.5` on Go1 and `q=0.5` on G1 as the same absolute skill level. The dataset report must separately list raw return, fall rate, episode length, and command statistics for every task and quality bin.

If not enough checkpoints fall into a bin, train the neutral collector longer. Do not silently use nearest checkpoints while still calling the dataset canonical `D_QS_core`.

### 6.4 Data Ratios and Training Sampler

The canonical dataset ratio is fixed before model comparison:

| Bucket | Ratio | Purpose |
|---|---:|---|
| random-smooth | 10% | broad coverage without pure iid action chaos |
| weak | 20% | failures, falling, recovery, early unstable gait |
| medium | 35% | partial skill, task-directed but diverse behavior |
| expert | 25% | stable high-return behavior |
| expert-noisy | 10% | local robustness around expert manifold |

This ratio is a design choice, not a paper claim. The first execution uses it as the main balanced dataset. Later, small sidecars should test ratio sensitivity:

```text
expert-heavy
medium-heavy
random-heavy
```

These sidecars can be 500 episodes/task; they do not need to match the 2k feasibility scale unless the first-pass results show dataset ratio is the dominant variable.

The collected dataset and the training sampler are different objects:

```text
D_QS_core:
  collected raw episode dataset

P_train_QS:
  bucket-balanced training sampling distribution over valid windows
```

Do not write the quality-stratified dataset as a weighted set union. A set union has no sampling weights. The raw dataset is the disjoint union of episode groups:

```math
\mathcal{D}_{\mathrm{QS}}
=
\cup
\mathcal{D}_{rs}
\cup
\mathcal{D}_{weak}
\cup
\mathcal{D}_{med}
\cup
\mathcal{D}_{exp}
\cup
\mathcal{D}_{exp-noise}.
```

The quality ratios define the canonical training sampling distribution:

```math
P_{\mathrm{train\_QS}}(b)
=
\begin{cases}
0.10 & b = \mathrm{random\_smooth},\\
0.20 & b = \mathrm{weak},\\
0.35 & b = \mathrm{medium},\\
0.25 & b = \mathrm{expert},\\
0.10 & b = \mathrm{expert\_noisy}.
\end{cases}
```

The same dataset must be used by:

```text
MLP WM
MLP ensemble WM
Flow WM
Residual Flow WM
Chunked WM
Transformer / latent-action WM
```

No model variant is allowed to receive a private dataset in the main comparison.

Episode ratio is not the same as training-window ratio. In locomotion, weak and random collectors may terminate early, while expert collectors may run to the time limit. Therefore, the training loader must support a bucket-balanced window sampler.

Canonical training sampler `P_train_QS`:

```text
1. sample quality bucket according to QS ratio
2. sample task uniformly unless a different task ratio is explicitly configured
3. sample episode uniformly within that task and bucket
4. sample a valid window within that episode
```

This enforces the intended training distribution:

```math
P(b)
=
\{0.10,0.20,0.35,0.25,0.10\}
\quad
\text{for}
\quad
b \in
\{\mathrm{random},\mathrm{weak},\mathrm{medium},\mathrm{expert},\mathrm{expert\text{-}noisy}\}.
```

The dataset report must separately show:

```text
episode ratio by bucket
raw window ratio by bucket
effective sampled window ratio by bucket
```

Uniform sampling over all materialized windows is allowed only as an ablation, not as the canonical WM training distribution.

Required sampler ablation:

```text
500 episodes/task sidecar:
  bucket-balanced sampler
  uniform-window sampler
```

This checks whether conclusions depend on artificial training reweighting. Result tables must include:

```text
dataset_distribution = raw_episode
training_sampler = bucket_balanced | uniform_window
```

### 6.5 Collector Action Definitions

Random-smooth:

```math
a_t = \alpha a_{t-1} + (1-\alpha)\epsilon_t,
\qquad
\epsilon_t \sim \mathcal{U}(-1,1),
\qquad
\alpha = 0.8.
```

Expert-noisy:

```math
a_t = \mathrm{clip}
\left(
\pi_{\mathrm{expert}}(s_t,c_t,e)
+
\epsilon_t,
-1,1
\right),
\qquad
\epsilon_t \sim \mathcal{N}(0,\sigma^2 I).
```

Use:

```text
sigma = 0.05 for main data
sigma in {0.05, 0.10, 0.20} for sidecar robustness data
```

The main dataset uses only `sigma = 0.05` to avoid turning expert-noisy into random-like data.

Expert-noisy diagnostics:

```text
clip_fraction_after_noise
mean_action_delta_norm
noise_to_action_std_ratio
expert_noisy_return_drop
expert_noisy_fall_rate
```

If `clip_fraction_after_noise` is high, expert-noisy becomes random-like. If `mean_action_delta_norm` and `noise_to_action_std_ratio` are near zero, expert-noisy is just expert duplication. The dataset report must flag both cases.

### 6.5.1 Action Convention

Store both normalized policy actions and environment-applied actions:

```python
episode["policy_action"] = float32[T, act_dim]  # policy output, normalized to [-1, 1]
episode["env_action"] = float32[T, act_dim]     # action after adapter scaling/clipping
episode["action_clipped"] = bool[T, act_dim]
episode["clip_fraction"] = float
episode["adapter_version"] = str
```

Canonical WM input:

```text
policy_action
```

Reason:

```text
Future policies in PWM/Flow-MBPO output normalized actions. The WM should therefore learn the transition as a function of the normalized action interface used by the policy. env_action is stored for auditing adapter behavior and debugging.
```

### 6.5.2 Command Distribution

For velocity-tracking tasks, command distribution must be fixed before collection.

Default training command range:

```text
v_x in [0.0, 1.0]
v_y in [-0.3, 0.3]
omega_z in [-0.5, 0.5]
```

Held-out command bins:

```text
high_forward:
  v_x in [1.0, 1.5]
  v_y in [-0.3, 0.3]
  omega_z in [-0.5, 0.5]

high_yaw:
  v_x in [0.0, 1.0]
  v_y in [-0.3, 0.3]
  |omega_z| in [0.5, 1.0]

lateral_heavy:
  v_x in [0.0, 1.0]
  |v_y| in [0.3, 0.6]
  omega_z in [-0.5, 0.5]

  command changes every 2 to 4 seconds within the training range
```

These bins should be sampled at episode generation time and labeled in metadata. Do not create OOD command tests only by post-hoc filtering continuous commands, because that can leak overlapping command distributions into train and test.

```math

\approx
4(T+1)d_{obs}
+
4T d_{act}
+
4T
+
T
+
4T d_{cmd}
```

### 6.9 Window Index Storage

Create windows by index:

```python
window = {
    "episode_id": int,
    "start_idx": int,
    "horizon": 16,
    "stride": 4,
    "split": "train|val|test|ood_command|ood_collector",
    "quality_bin": str,
}
```

The training loader materializes:

```math
(s_{t:t+H}, a_{t:t+H-1}, r_{t:t+H-1}, d_{t:t+H-1}, c_{t:t+H-1}, e).
```

This avoids duplicating overlapping windows and makes split auditing easy.

Window boundary rule:

```text
No training window may cross a true termination boundary.
```

If an episode terminates because of a fall, windows ending before the fall may be used and labeled as fall-adjacent. Windows that would map a terminal fall state into a reset initial state must be excluded from WM dynamics training.

Timeout truncation is handled separately:

```text
true termination:
  do not cross boundary

timeout truncation:
  may be used up to the final valid transition, but do not append reset state as next state
```

The termination head can remain optional in Stage 2, but termination masking and boundary handling are not optional.

Minimum valid-window gate for A2.5:

```text
For every task x quality_bin:
  at least 50 train episodes
  at least 10k valid H16 train windows after termination masking
```

With an 80/10/10 split and the QS ratio, 500 total episodes/task may leave only 40 train episodes in the 10% buckets. Therefore A2.5 should use:

```text
nominal target:
  500 episodes/task

overcollect if needed:
  up to 625 episodes/task
  or directly enforce per-bucket train minimums
```

The count that matters for A2.5 validity is the post-split train count and valid-window count, not the nominal total episode target.

If this gate fails, A2.5 can still run as:

```text
preliminary_sampler_debug
```

but it cannot be used to judge Flow feasibility.

### 6.10 Splits

Splits must be by episode, not by window:

```math
\mathcal{E}_{train}
\cap
\mathcal{E}_{val}
=
\emptyset,
\qquad
\mathcal{E}_{train}
\cap
\mathcal{E}_{test}
=
\emptyset.
```

Within each task and quality bucket:

```text
train: 80%
ID val: 10%
ID test: 10%
```

Additional held-out tests:

```text
held-out command test:
  commands excluded from training command ranges

held-out collector checkpoint test:
  checkpoint qualities not used in training but within same quality region

held-out collector seed test:
  at least one collector seed held out if enough data exists

held-out task / embodiment test:
  only for Paper v1 or later
```

Held-out command episodes have two independent labels:

```text
quality_bin:
  based on train-range collector evaluation

command_bin:
  train | high_forward | high_yaw | lateral_heavy | command_switch
```

Do not mix OOD command rollouts into `D_QS_core` training unless the dataset version explicitly says so.

Phase-A gate split:

```text
Primary gate:
  train / ID val / ID test on D_QS_core

Secondary report:
  held-out command test
```

Held-out command results are required for the report, but they do not decide whether Flow WM is feasible in Phase-A. The first feasibility question is in-distribution fitting under a correctly collected fixed dataset.

Do not report only train/val. Report at least train, ID val, ID test, and held-out command if command logging is available.


Training budget policy:

```text
Phase-A equal-update pass:
  all models use the same train_iters.

Phase-A Flow-push pass:
  Flow-based models may train longer only if the equal-update pass satisfies the pre-registered trigger.
  allowed multipliers: 2x and 4x train_iters.

Compute-matched pass:
  optional later analysis, not required for the first feasibility answer.
```

Rationale:

```text
The first question is whether Flow can fit or win at all under fixed data.
If Flow needs more compute, we record that cost rather than blocking the feasibility test.
```

Flow-push trigger:

```text
1. Validation normalized H16 rollout loss improves by >= 5%
   over the final 20% of evaluation points.
2. No divergence or latent norm explosion.
3. Equal-update normalized H16 rollout loss is <= 20x mlp_ref, not hundreds of times worse.
4. Reward loss is not diverging:
   final validation reward loss <= 2x best validation reward loss
   and no NaN/Inf appears in train or validation reward loss.
```

If these conditions are not met, do not submit automatic 2x/4x Flow-push jobs. In that case, record the result as a formulation failure candidate rather than spending more compute.

Paper-framing rule:

```text
equal_update:
  main fair feasibility result

flow_push_2x / flow_push_4x:
  existence or upper-bound diagnostic only

flow_train_loss_match_300k:
  existence diagnostic that lets Flow train up to 300k updates against a fixed 50k-update MLP target.
  This is not an equal-compute or equal-update comparison.

compute_matched:
  later efficiency comparison
```

A Flow model that fails equal-update but passes only under Flow-push is not a fair replacement for MLP WM. It is evidence that the formulation may be trainable with extra compute.

Train-loss-match sidecar:

```text
Purpose:
  test whether Flow can eventually reach the MLP training rollout dynamics loss
  when allowed substantially more optimization.

Reference target:
  Train mlp_ref for exactly 50k updates on the same fixed D_QS_core split.
  Record train/rollout_dyn_mse_H16 at the selected MLP checkpoint.

Flow budget:
  Train flow_ref up to 300k updates.
  Stop early only if Flow reaches:
    flow_train_rollout_dyn_mse_H16 <= mlp_train_rollout_dyn_mse_H16 * (1 + tolerance)

Default tolerance:
  5%

Required logging:
  mlp_train_iters
  mlp_wall_clock_seconds
  mlp_train_rollout_dyn_mse_H16
  flow_max_iters = 300000
  flow_iters_to_stop
  flow_wall_clock_seconds
  flow_matched_mlp_train_loss
  flow_train_loss_ratio_to_mlp
  extra_flow_iters_vs_mlp
  flow_to_mlp_wall_clock_ratio
  final train/val/test rollout metrics for both MLP and Flow

Interpretation:
  If Flow matches only after extra training, the result says Flow is trainable with additional compute.
  It does not show that Flow is a fair replacement for MLP under equal updates or equal compute.
```

Primary metrics:

```text
train/one_step_dyn_mse
val/one_step_dyn_mse
test/one_step_dyn_mse

train/normalized_one_step_dyn_mse
val/normalized_one_step_dyn_mse
test/normalized_one_step_dyn_mse

val/rollout_dyn_mse_H8
test/rollout_dyn_mse_H8
```

Rollout error curve:

```math
e_h
=
\mathbb{E}
\left[
\left\|
\hat z_{t+h}
-
\mathrm{sg}(E_\phi(o_{t+h},c_{t+h},e))
\right\|_2^2
\right],
\qquad
h=1,\ldots,H.
```

Feasibility success criterion:

```math
\frac{
\mathcal{L}^{train,H=16}_{dyn,\mathrm{candidate}}
}{
\mathcal{L}^{train,H=16}_{dyn,\mathrm{mlp\_ref}}
}
\leq 3
```

and:

```math
\frac{
\mathcal{L}^{val,H=16}_{dyn,\mathrm{candidate}}
}{
\mathcal{L}^{val,H=16}_{dyn,\mathrm{mlp\_ref}}
}
\leq 5
```

on both diagnostic tasks.

The ratio criterion is not sufficient by itself. Also require:

```text
Gate A: train H16 rollout loss
  candidate <= 3x mlp_ref
  OR candidate <= absolute normalized threshold tau_train

Gate B: validation H16 rollout loss
  candidate <= 5x mlp_ref
  OR candidate <= absolute normalized threshold tau_val

Gate C: rollout error curve shape
  e_16 / max(e_1, epsilon) <= rho_rollout

Gate D: reward loss
  candidate reward loss <= 2x mlp_ref reward loss

Gate E: bounded latent rollout
  predicted_latent_norm remains finite and within 2x target_latent_norm median
```

Initial thresholds:

```text
tau_train = 1e-3 if latents are normalized similarly to previous MLP runs
tau_val = 1e-2 if latents are normalized similarly to previous MLP runs
rho_rollout = 100
epsilon = 1e-8
```

These absolute thresholds must be recalibrated after Stage -1 if latent scaling changes. The final report should show both ratio-based and absolute metrics.

Strict interpretation:

```text
If no Flow-based WM passes this gate, Flow WM is downgraded to exploratory.
Do not run Flow WM as a main downstream policy model.
```

If residual/chunked Flow passes but pure Flow fails:


Effective signal-to-noise ratio:

```math
\mathrm{ESNR}(g)
=
\frac{
\left\|
\mathbb{E}[g]
\right\|_2^2
}{
\mathbb{E}
\left[
\left\|
g-\mathbb{E}[g]
\right\|_2^2
\right]
+\epsilon
},
```

where `g = grad_theta J_model(theta)` estimated across minibatches.

Exit criterion:

```text
At least one pretrained WM supports real-env policy improvement above random and above untrained policy.
```

If MLP WM works but Flow WM fails:

```text

```

If MLP WM + Flow policy works:

```text

```

## 10. Main Decision Rules

### Rule 1: No Dataset Changes After Model Comparison Starts

Once `D_QS_core` is frozen, do not change it based on Flow results. Any later dataset is a new dataset version.

### Rule 2: Same Data for All WM Variants

All main WM variants train on identical episodes and splits.

### Rule 3: No Silent Task Fallback

Fallback-permitted data may be used only for exploratory runs. Canonical datasets require exact resolved task IDs.

### Rule 4: Do Not Enter Full 2x2 Until WM Feasibility Passes

If Flow-based WM variants cannot reach within `3x` train rollout dynamics loss and `5x` validation rollout dynamics loss of `mlp_ref`, they are not main downstream WM candidates.

### Rule 5: Report Compute

Flow models have ODE integration overhead. Always report wall-clock, GPU type, and compute-normalized reward.

Compute parity is not required for the first feasibility pass. The first pass may include extended Flow training to test whether Flow can fit at all. However, every result table must mark:

```text
equal_update
flow_push_2x
flow_push_4x
compute_matched
```

so we do not confuse "Flow can win with more compute" with "Flow is compute-efficient."

Flow-push is pre-registered, not arbitrary post-hoc rescue. It can be launched only when the equal-update learning curve is still improving and the model is not diverging. The trigger is defined in Stage 2.

## 14. Final Standard

The restart is successful only if we can answer these questions cleanly:

1. What exact real data was used?
2. Which collector policy produced each episode?
3. What task was actually resolved at runtime?
4. Did the WM fit train, validation, and held-out splits?
5. Is the failure in reward prediction, one-step dynamics, or multi-step rollout dynamics?
6. Does the pretrained WM improve real MJLab policy learning?
7. Does Flow help on the WM side, policy side, both, or neither?

If we cannot answer all seven questions from artifacts and CSVs, the experiment is not paper-grade.
